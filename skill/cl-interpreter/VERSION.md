## 0.3.0 (2026-10-22) — 지식의 출처 위계와 구조 개편
이번 판은 구조와 인용 방식을 바꾼 것이다. 실행 검증 전인 내용을 확정으로 올린 것은 없다.

### 지침
- 찾는 순서를 정했다: 공식 문서 → 충돌 파일 → 판정 → 3일치 → 가설. 정의는 공식 문서에서 먼저 확인한다.
- 3일치는 정의가 아니라 특정 코드의 적용 예제로 인용한다("비슷한 코드에서는 ~로 해석됩니다").
- 답에 보이는 태그 이름을 바꿨다: 3일치 → *추가검증필요*(잠정), 가설 → *예상*. 지식 파일 안의 내부 등급 표기는 그대로다.
- 캡처 전사 뒤 연산자·괄호를 다시 대조하고, 연산자 하나에 달린 해석은 그 사실을 밝힌다.
- 오류 후보를 세 갈래(명백한 오류 / 공식 목록과 불일치 / 이 자료에서 확인 안 됨)로 나누고, 주석과 코드의 이름 불일치와 같은 인자 반복을 넣었다. 값이나 의도만 이상한 것은 오류 절에 올리지 않는다.
- *공식 문서* 태그는 공식 문서에 그대로 적힌 내용에만 단다. 이 코드의 변수·값·조건에 적용한 문장은 *코드 추론*이다.
- 짧은 문법 질문에는 보고서 형식 대신 2~5문장으로 답한다.
- 축약 지침의 답변 순서(M.E.M.O 위치)를 SKILL.md에 맞췄다.
- 사용자 검토 반영(2026-10-22): 3일치 중 75건을 검토해 68건을 판정 확정으로 올렸다(정의 층 18 → 86건, 예제 층 3일치 209 → 141건). 7건은 보류. 확정된 10건의 "실행검증 필요" 표시를 해제했다. C-adv-13 판정(lhs − rhs)으로 differenceFunction 부호 충돌을 해소하고, `this`(D-concept-05)를 *판정*으로 쓰게 했다. 내역은 레포의 `knowledge/검토반영_2026-10-22.md`.
- 재측정 뒤 보완: `this` 설명은 사례형으로 쓴다(정의형 인용 2건 대응). 예제 파일의 "판정 항목의 보충"을 찾으면 grammar-defs.md의 같은 ID도 본다(층 혼동 1건 대응, 보충 항목 제목에도 표시). 오류 절에 쓴 내용은 M.E.M.O로 다시 쓰지 않는다(3회 반복 대응).

### 지식 파일
- `grammar-draft.md`(약 240KB)를 패키지에서 빼고 두 층으로 나눴다. 원본은 레포의 `knowledge/grammar-draft.md`에 그대로 있다.

## 갱신 방법
1. Amplify에서 `cl-knowledge-build/knowledge/실행검증대상.md`의 항목을 실행해 통과/실패를 기록한다.
2. 통과한 항목은 레포의 `knowledge/grammar-draft.md`의 등급을 "실행 확인"으로 올리고, 실패한 항목은 확정 문장을 고친다. 충돌(`reference/conflicts.md`)은 실행 결과로 해소한다. 그다음 `도구/split_grammar.py`로 정의 층과 예제 층을 다시 만든다.
3. 공식 문서가 바뀌면 `cl-knowledge-build/도구/build_skill_knowledge.py`를 다시 실행해 official-*.md와 site-core.md를 새로 만든다 (원본: computation-layer-master/data).
4. 배포 ZIP은 `도구/make_zip.py`로 만든다. 버전과 날짜를 이 파일에 적는다.
5. ZIP을 만들기 전에 설치 안내(`guides/`)에 옛 버전 파일명이 남아 있는지, 대체 구성의 업로드 목록이 SKILL.md가 참조하는 파일(`reference/conflicts.md` 등)을 모두 포함하는지 확인한다.
